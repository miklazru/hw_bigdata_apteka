# ADR-0004. Остаток материализован, а не считается из журнала

**Статус:** принято · **Дата:** 2026-10-13

## Контекст
Контракт `v_stock` — остаток партии в локации с `updated_at`. Инвариант I7:
остаток не может стать отрицательным ни вставкой, ни списанием.
Источник правды о движении товара — журнал `movement`.

## Рассмотренные варианты
1. **Остаток вычисляется из журнала** (`v_stock` = `SUM` по `movement`).
   Нет дублирования данных. Отвергнут: I7 придётся держать триггером, который
   при каждой вставке пересчитывает сумму по всему журналу партии в локации —
   медленно и требует блокировок от гонок; у вычисленного остатка нет честного
   `updated_at` для инкрементальной выгрузки.
2. **Материализованное представление, обновляемое по расписанию.** Отвергнут:
   между обновлениями остаток устаревший, а I7 на нём вообще не выразить.
3. **Таблица `stock`, обновляемая триггером на `movement`.** Выбран.

## Решение
`stock (location_id, batch_id, qty_on_hand numeric CHECK (qty_on_hand >= 0),
updated_at)`, PK `(location_id, batch_id)`. Триггер `AFTER INSERT` на `movement`
уменьшает остаток в источнике и увеличивает в получателе (`INSERT ... ON CONFLICT
DO UPDATE`). Попытка списать больше, чем есть, нарушает `CHECK` → `23514` (I7);
вся транзакция с движением откатывается.

## Цена решения
* Данные дублируются: остаток = функция журнала, и при ошибке в триггере они
  разойдутся. Компенсация — сверочный запрос «stock = SUM(movement)» в тестах.
* `movement` становится append-only: исправление движения — только сторнирующим
  движением, иначе остаток надо пересчитывать.
* Каждая вставка в журнал — ещё две записи в `stock` (горячие строки при
  параллельной нагрузке на одну партию).
