# ADR-0006. История атрибутов SKU и клиента — журнал через триггер

**Статус:** принято · **Дата:** 2026-10-13

## Контекст
Название SKU, его категория (и, следовательно, рецептурность) меняются со
временем. У клиента меняются уровень лояльности и город. Требование 4:
история там, где атрибут меняется. Значения «на момент продажи» уже
сохраняются snapshot-полями в позиции чека.

## Рассмотренные варианты
1. **Не хранить — DWH получит историю через CDC.** Отвергнут: история
   появится только с момента запуска CDC, всё, что было до, потеряно; источник
   сам по себе не может ответить «когда переименовали».
2. **SCD2-версии (`sku_version` с `valid_from/valid_to/is_current`).**
   Удобно для запросов «как было на дату». Отвергнут: каждое чтение текущего
   SKU — JOIN на текущую версию, каждое изменение — две операции; при этом
   запросов «на дату» к атрибутам SKU почти нет (snapshot в чеке уже есть).
3. **Текущее состояние в основной таблице + журнал изменений, который пишет
   триггер.** Выбран.

## Решение
Общая функция `log_attr_change()` в каждой базе. Триггер `AFTER UPDATE`
на `catalog.sku` (атрибуты `sku_name`, `category`) и `crm.customer`
(`loyalty_level`, `city`, `region_code`) пишет `(entity_id, attr_name,
old_value, new_value, changed_at)` в `sku_history` / `customer_history`.
Приложение делает обычный `UPDATE`; забыть записать историю невозможно.

## Цена решения
* Значения в журнале хранятся как `text` — типизация теряется.
* Восстановить состояние «на дату» можно, но запросом по журналу, а не простым
  фильтром по интервалу.
* Журнал растёт с каждым изменением; для чистки нужна отдельная политика.
