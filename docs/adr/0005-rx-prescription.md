# ADR-0005. I10: snapshot рецептурности и рецепт на уровне позиции

**Статус:** принято · **Дата:** 2026-10-13

## Контекст
Инвариант I10: рецептурный препарат не отпускается без рецепта. Признак
рецептурности живёт в `catalog_service`, а ограничение нужно в `pos_service`.
Обращаться в чужую базу из ограничения нельзя (разные системы, нет FK, нет
dblink в проде). Контракт отдаёт один `prescription_bk` на чек.

## Рассмотренные варианты
1. **Проверять признак в каталоге в момент продажи** (dblink / FDW / вызов
   сервиса из триггера). Отвергнут: связывает две системы физически, касса
   встаёт при недоступности каталога; кроме того, задним числом признак может
   измениться, и проверка станет невоспроизводимой.
2. **Snapshot `is_rx` в позиции + рецепт на уровне чека + триггер на позицию**
   («если строка rx — у чека должен быть рецепт»). Работоспособно, код `P0001`.
   Отвергнут: триггер там, где можно обойтись `CHECK`; один рецепт на весь чек
   не отражает реальность (в чеке могут быть два rx-препарата по двум рецептам).
3. **Snapshot `is_rx` в позиции + рецепт на уровне позиции + `CHECK`.** Выбран.

## Решение
Требование к модели: **POS хранит `is_rx_snapshot` у себя** — значение,
полученное из каталога в момент продажи. В `receipt_line` — колонка
`prescription_id` (FK на `prescription`) и
`CHECK (NOT is_rx_snapshot OR prescription_id IS NOT NULL)` → `23514`.
`v_receipt.prescription_bk` = `min(prescription_bk)` по позициям чека.

## Цена решения
* Контракт теряет детализацию: при двух рецептах в чеке наружу уходит один.
* Корректность snapshot — ответственность приложения/интеграции: если касса
  получила устаревший признак, БД это не поймает (X10 проверяет мягко, 5%).
* Возврат rx-позиции копирует рецепт из исходной строки — иначе C04.
