# ADR-0010. Soft delete через `deleted_at`, `updated_at` через триггер

**Статус:** принято · **Дата:** 2026-10-13

## Контекст
DWH (ДЗ2) забирает изменения инкрементально по `updated_at` и через CDC.
Удаление в справочниках должно быть видно хранилищу; физическое удаление
клиента запрещено.

## Рассмотренные варианты
1. **Физический `DELETE`.** Отвергнут: удалённую строку инкремент по
   `updated_at` не увидит никогда; ломает ссылки из фактов (чеки на клиента).
2. **`is_deleted boolean`.** Отвергнут: хранит факт, но не момент удаления —
   а он нужен DWH, чтобы закрыть интервал версии.
3. **`deleted_at timestamptz NULL`.** Выбран.
4. Для `updated_at`: **заполняет приложение** — отвергнут (забудет —
   изменение не попадёт в DWH); **триггер `BEFORE UPDATE`** — выбран.

## Решение
В справочниках `deleted_at timestamptz NULL`; «удаление» — `UPDATE`, который
меняет и `updated_at`, поэтому видно инкременту. Признак `is_active` во view —
`deleted_at IS NULL` (для аптек — ещё и `closed_at IS NULL`). Общая функция
`set_updated_at()` вешается `BEFORE UPDATE` на все таблицы. Плюс
`created_at DEFAULT now()` и `source_system DEFAULT '<код сервиса>'`.

## Цена решения
* Каждый запрос к справочнику обязан помнить про `deleted_at IS NULL`
  (снаружи это скрывают представления `contract`).
* Удалённые строки занимают место и BK навсегда — BK не переиспользуется
  (для DWH это плюс).
* Ручная правка `updated_at` невозможна (например, при исторической загрузке
  генератор получит `now()`); для backfill триггер проверяет
  флаг сессии `app.backfill`.
